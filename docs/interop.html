interop

The DOM engine is not the edge of this library, it is one consumer of it. Underneath sits a function that takes two numbers and returns one, and that function does not care whether the result becomes a bar height, a vertex, a filter cutoff or a CSS easing curve. This page is about handing that number to something else: three.js first, then the other runtimes worth knowing about.

One function is the whole surface

Everything on this page rests on a single call:

const s = VanillaWaves.createSampler({ shift: true, group: 'gentle', range: [-1, 1] });
s.sample(position, time);   // number in, number out

That is the entire integration surface. No canvas, no DOM, no renderer, no clock: you pass t in seconds yourself, so you can scrub it, freeze it, run it backwards or run it faster than real time. A renderer only has to answer one question: which of my numbers should this drive?

why it matters The wave dialect is not a noise function. It is a curated set of 35 named shapes with periods, groups, and a shift engine that morphs between them. Everything a renderer gains from that comes through sample(), so nothing about the port's DOM engine limits where it can go.

Loading it next to a module-based renderer

Most 3D and 2D renderers ship as ES modules today, so the library meets them there. waves-core.mjs is the module entry point on the math:

// the module route - same file works in the browser, in Node and in bundlers
import { createSampler, wave, list } from './waves-core.mjs';
import * as THREE from 'three';

const s = createSampler({ shift: true, group: 'gentle', range: [-1, 1] });

That file holds no math of its own. It imports waves-core.js for its side effect and re-exports the result, so there is exactly one copy of the canonical formulas and the module layer cannot drift away from it. It also leaves the globals in place, so mixing the two routes in one page is harmless.

on the CDN Since v0.3.1 the module entry ships on jsDelivr: import { createSampler, wave, list } from 'https://cdn.jsdelivr.net/gh/seb-prjcts-be/vanilla.waves@v0.3.1/waves-core.mjs'; Or copy it next to your code for a fully local, zero-dependency setup.

The classic route still works and is what you want when the DOM engine comes along, since the engine is browser-only and self-initialising. Load the script first, read the global inside your module:

<script src="waves-core.js"></script>
<script type="importmap">
  { "imports": { "three": "https://cdn.jsdelivr.net/npm/three@0.169.0/build/three.module.js" } }
</script>
<script type="module">
  import * as THREE from 'three';
  const W = globalThis.VanillaWaves;   // globals are visible inside modules
</script>

Reach for waves-core rather than the full bundle when the DOM engine is not going to be used: it is the math alone, with no shared loop and no [data-wv] scanning.

Node takes the same module entry, which is what makes an adapter testable without a browser, a GPU or a renderer:

import { createSampler } from '../vanilla.waves/waves-core.mjs';   // 35 waves, ready

The adapter rule

The mistake is to sprinkle sample() calls through renderer code. The pattern that holds up is a thin layer in between that knows the waves but deliberately does not know the renderer: it takes a position and a time, and returns plain numbers.

// wave-field.js - imports nothing, knows no renderer
export function createWaveField(W, opts = {}) {
  const a = W.createSampler({ seed: 7,  shift: true, group: 'gentle', range: [-1, 1] });
  const b = W.createSampler({ seed: 19, shift: true, group: 'gentle', range: [-1, 1], phase: 1.7 });

  return {
    sample(x, z, t, out = {}) {
      const u = a.sample(x * 0.62 + z * 0.31, t);
      const v = b.sample(z * 0.62 - x * 0.31, t);
      const angle = (u * 0.78 + v * 0.22) * Math.PI;
      const y = v * 0.32;                              // tilt
      const flat = Math.sqrt(Math.max(0, 1 - y * y));  // keep it unit length
      out.x = Math.cos(angle) * flat;
      out.y = y;
      out.z = Math.sin(angle) * flat;
      return out;
    },
    get waveName() { return a.waveName; },
    get target()   { return a.targetName || ''; }
  };
}

Three things fall out of that boundary, and they are the reason to draw it:

  • It is testable in Node. Normalisation, finiteness, bounds and reproducibility can all be asserted without a canvas. A field that returns NaN at one grid position is a silent visual glitch in a renderer and a failing test in Node.

  • It outlives the renderer. The same field can drive line segments today and particles, meshes, cameras, lights or shader uniforms tomorrow, with no change to the wave code.

  • It keeps the readout honest. Exposing waveName and targetName means the scene can show which formula is playing and which one is coming, which is how you debug motion you cannot pause.

worked proof three.waves, a companion experiment, folds two samplers into one normalised 3D direction and drives 576 line segments through a single BufferGeometry. Its adapter has no three.js import at all and is covered by Node tests for normalisation, reproducibility, shift and hard height bounds. Measured there: 600 updates of 576 vectors in 125 ms, about 0.21 ms per full field update, wave math only.

three.js: displaced geometry

The plainest useful case. Walk a BufferAttribute, read one sampler per vertex, flag it dirty. Position enters as the first argument, time as the second, so the line both has a shape along its length and moves.

const N = 200;
const geo = new THREE.BufferGeometry();
const pos = new Float32Array(N * 3);
geo.setAttribute('position', new THREE.BufferAttribute(pos, 3));
scene.add(new THREE.Line(geo, new THREE.LineBasicMaterial({ color: 0x00b3a4 })));

const s = W.createSampler({ shift: true, group: 'gentle', range: [-1.2, 1.2] });

function frame(t) {
  for (let i = 0; i < N; i++) {
    pos[i*3]     = (i / (N - 1)) * 12 - 6;   // x across the line
    pos[i*3 + 1] = s.sample(i * 0.6, t);     // y from the wave
    pos[i*3 + 2] = 0;
  }
  geo.attributes.position.needsUpdate = true;
  geo.computeBoundingSphere();               // or frustum culling misjudges it
}

Reuse one Float32Array and one sampler; do not rebuild geometry per frame. Mark the attribute with setUsage(THREE.DynamicDrawUsage) when it changes every frame.

three.js: the seamless closing ring

This is the pattern that has no equivalent in a noise library, and it is the strongest reason to reach for the wave dialect in 3D.

Sweep any wave around a ring and the last point almost never lands on the first, so the shape tears at the seam. The fix is to sweep an integer multiple of the wave's period. That alone is easy for one fixed wave and normally impossible with shift on, because every formula has its own period and the seam rips open the moment the library lands on a new wave. The 'closing' pool exists for exactly this: its 19 waves all share one base period, so a sweep of sampler.period × lobes stays closed through every transition.

const SEG = 240, LOBES = 6;
const ring = W.createSampler({ shift: true, group: 'closing', range: [-0.6, 0.6] });

function frame(t) {
  const sweep = ring.period * LOBES;   // read the sweep off the sampler
  for (let i = 0; i <= SEG; i++) {
    const u   = i / SEG;
    const ang = u * Math.PI * 2;
    const r   = 2 + ring.sample(u * sweep, t);
    pos[i*3]     = Math.cos(ang) * r;
    pos[i*3 + 1] = 0;
    pos[i*3 + 2] = Math.sin(ang) * r;
  }
  geo.attributes.position.needsUpdate = true;
}

How closed is closed? Measured on a ring of radius 2 over 120 frames of active shifting, the worst gap between the first and last vertex was 1.3e-5 world units, which is far below one pixel at any sane camera distance. The same test against the raw sampler shows what the pool buys you: over 30 seconds of shifting at amplitude 30, the worst seam error is 0.005 with group: 'closing' and 28.7 with group: 'all'.

Anything swept and closed inherits this: rings, tubes, lathe profiles, torus cross-sections, orbit paths, extrusions along a loop.

experimental Period values may drift by about 0.001 in minor versions. Perfect for visuals, not for plotters or CNC.

three.js: an instanced 2D field

There is no createGrid() in the dialect any more, and it is not missed: a 2D field is two samplers and your own loop, which is also what lets you decide how the two axes combine. Feed the result to an InstancedMesh and thousands of objects cost one draw call.

const GX = 16, GZ = 16;
const mesh = new THREE.InstancedMesh(
  new THREE.BoxGeometry(0.4, 1, 0.4),
  new THREE.MeshStandardMaterial({ color: 0x00b3a4 }),
  GX * GZ
);
const sx = W.createSampler({ seed: 7,  shift: true, group: 'gentle', range: [0, 1] });
const sz = W.createSampler({ seed: 21, shift: true, group: 'gentle', range: [0, 1] });
const dummy = new THREE.Object3D();

function frame(t) {
  let i = 0;
  for (let gz = 0; gz < GZ; gz++) for (let gx = 0; gx < GX; gx++, i++) {
    const h = 0.2 + sx.sample(gx * 1.5, t) * sz.sample(gz * 1.5, t) * 3;
    dummy.position.set(gx - GX/2 + 0.5, h/2, gz - GZ/2 + 0.5);
    dummy.scale.set(1, h, 1);
    dummy.updateMatrix();
    mesh.setMatrixAt(i, dummy.matrix);
  }
  mesh.instanceMatrix.needsUpdate = true;
}

Multiplying the two axes gives interference and standing-wave patterns; adding them gives soft diagonal ridges. Both are one character apart, so try each.

three.js: the wave as a GPU lookup

Per-vertex CPU sampling stops scaling somewhere in the tens of thousands. The way out is to stop sampling per vertex and sample the wave once into a small texture, then let the shader read it. The CPU does 256 wave evaluations per frame instead of 200,000, and the GPU does the rest.

const LUT  = 256;
const data = new Float32Array(LUT);
const tex  = new THREE.DataTexture(data, LUT, 1, THREE.RedFormat, THREE.FloatType);
const s    = W.createSampler({ wave: 'mountain peaks', range: [0, 1] });

const mat = new THREE.ShaderMaterial({
  uniforms: { uLut: { value: tex } },
  vertexShader: `varying vec2 vUv;
    void main(){ vUv = uv; gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0); }`,
  fragmentShader: `uniform sampler2D uLut; varying vec2 vUv;
    void main(){
      float v = texture2D(uLut, vec2(vUv.x, 0.5)).r;
      gl_FragColor = vec4(vec3(step(vUv.y, v)), 1.0);
    }`
});

function frame(t) {
  for (let k = 0; k < LUT; k++) data[k] = s.sample(k * 0.7, t);
  tex.needsUpdate = true;   // one small upload per frame
}

Bake once instead of every frame when the wave is frozen (shift: false and a fixed t), and the per-frame cost drops to zero. This is also how a wave reaches a vertex shader: read the LUT in the vertex stage and displace there.

Other runtimes worth knowing about

Nothing above is specific to 3D. Any host with a number-shaped input is a candidate, and some of these fit the dialect unusually well.

HostThe seam
Web AudioA wave is an LFO. Fill a Float32Array from the sampler and hand it to AudioParam.setValueCurveAtTime() to steer a cutoff, detune or gain over a fixed span. Same idea in Tone.js.
CSS easingBake N samples into a linear() timing function once, and the animation runs with no JavaScript at all afterwards. A wave becomes an easing curve.
CSS variablesel.style.setProperty('--wv', s.sample(0, t)) and let stylesheets decide what it means. One JS write, many visual consequences.
GSAPUse it inside a modifiers function or a ticker callback so GSAP owns the timeline and the wave owns the shaping.
Canvas 2D / PixiIdentical to the three.js loop without the geometry step: sample per element, write a coordinate, a radius or a colour.
SVG / D3Feed a path generator, or produce plausible placeholder series for skeleton charts that move instead of shimmering.
PhysicsMatter.js and friends: a wave as a force over time, or as the path of a moving platform or attractor.
Node, build timeNo renderer at all. Bake SVG paths, LUT textures or static frames ahead of time, so the browser ships zero wave code.

the tell If a host exposes a number you can write every frame, or an array it will interpolate for you, the sampler already fits. Reach for the adapter rule before the second one of these.

The module entry point, and what it is not

waves-core.mjs is a shim of about a dozen lines. It contains no formulas: it imports waves-core.js for its side effect and re-exports what that installs.

import './waves-core.js';

const W = globalThis.VanillaWaves;

export const wave          = W.wave;
export const createSampler = W.createSampler;
export const list          = W.list;
export const data          = W.data;
export const count         = W.count;
export default W;

That shape is deliberate. Re-exporting rather than re-implementing means there is one copy of the canonical math in the repo, so the module layer cannot drift from the p5.waves baseline the port is measured against. Verified across both runtimes: the detached exports are bit-identical to the global over a thousand calls, and Node and the browser return the same digits for the same input.

WorksDetail
Browser ESMimport { createSampler } from './waves-core.mjs'
NodeSame import. waves-core.js loads as CommonJS there; the globalThis assignment is identical either way.
BundlersResolves as a normal module. No build step: unlike the bundles, this file is written, not generated.
GlobalsStill installed, so the module route and the <script> route can coexist on one page.

Two limits are worth stating plainly. There is no npm package, so a bare specifier like import ... from 'vanilla.waves' does not resolve: import it by path, or map it yourself. And because the exports come off one frozen object rather than being separate module bindings, a bundler cannot tree-shake the unused waves out. For a zero-dependency file this size that is a fair trade, but it is better known now than halfway into a build setup.

not included The DOM engine is not part of the module entry. It is browser-only and initialises itself on DOMContentLoaded, so it stays where it belongs: load vanilla.waves.js with a <script> tag when you want register, init and destroy.
